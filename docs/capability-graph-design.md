# 能力图谱（Capability Graph）细化设计

> 版本：v0.2 ｜ 日期：2026-11-16 ｜ 上游文档：`learning-app-5-designs.md` 方案 A
> 本文只做设计，不含实现代码。目标是"照着能开工"。

---

## 1. 相对 v0.1 改了什么

上一版方案 A 只说了"证据 + 衰减"，这一版把四个含糊的地方钉死：

| 项 | v0.1 | v0.2 修订 | 为什么改 |
|---|---|---|---|
| 掌握度 | 证据强度加权累计 | **分层覆盖**（四个难度层各自封顶），单纯刷低难度拿不到高分 | 累计会让"做了 100 道 D1 题"等于"能做架构决策" |
| 衰减 | 统一 0.92 系数 | **双参数**：记忆半衰期（时间函数）+ 技术过时事件（事件驱动） | 框架 API 不是"忘了"，是"废了"，两者机制不同 |
| 评分数值 | 只给公式 | 给完整数值示例，一天算出 83 分 | 无示例的公式无法验收 |
| 置信度 | 无 | 新增 `confidence`，低证据时显示"未验证"而非低分 | 避免 0 分节点对新用户的打击 |

## 2. 图谱本体

### 2.1 四层结构

```
Domain（六大区）        ← 只用于分区展示，不参与计算
  └ Topic（主题）        ← 页面的折叠分组
      └ Node（原子能力）  ← 唯一可评分单位，掌握度挂在这里
          └ Evidence（证据）← 不展示为节点，是节点的"传感器"
```

关键约束：**只有 Node 有掌握度**。用户看到的"我点亮了什么"和分数计算用的是同一批对象，不出现"完成度"和"掌握度"两套数字。

### 2.2 六大区与节点预算

| 区 | 节点数（全量） | 说明 |
|---|---|---|
| 语言与范式 | 40 | JS 核心、TS 类型系统、编程范式 |
| 浏览器与网络 | 35 | 渲染管线、事件、存储、HTTP、安全 |
| 框架与应用架构 | 30 | 组件模型、状态、路由、数据获取、SSR |
| 工程化与质量 | 25 | 构建、包管理、Lint、测试、CI |
| 性能与可观测 | 20 | 指标、加载优化、运行时优化、监控 |
| 界面与可访问 | 30 | 布局、设计还原、a11y、动效、响应式 |
| **合计** | **180** | v0.1 说 120–200，这里定 180 |

**第一版不建 180 个，只建 40 个**（语言 20 + 浏览器 20）。理由见第 9 节。

### 2.3 节点字段规范

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | slug | 是 | 全局唯一，如 `js.event-loop` |
| `name` | string | 是 | 用户可见名称，短，不带框架黑话 |
| `domain` / `topic` | enum | 是 | 归属 |
| `definition` | string | 是 | **一句话，且必须是可验证的**。写"理解事件循环"不合格；写"能说出给定一段含 setTimeout/Promise 的代码的输出顺序，并解释原因"合格 |
| `why` | string | 是 | 不学它会怎样。这一栏决定用户是否愿意投入 |
| `job_weight` | 1–5 | 是 | 岗位价值权重，来自 JD 语料频次（见 9.1） |
| `prerequisites` | id[] | 是 | 硬前置，可为空 |
| `related` | id[] | 否 | 软关联，用于推荐 |
| `memory_half_life` | days | 是 | 记忆半衰期，见 3.5 |
| `eol_events` | json | 否 | 技术过时事件（如"某 API 废弃"） |
| `evidence_ladder` | json | 是 | 该节点可接受的证据类型与基准强度（见 3.2） |
| `self_checks` | json | 是 | 每个难度层至少 2 题 |
| `misconceptions` | string[] | 是 | 至少 2 条常见误区，用于随机抽查 |
| `in_the_wild` | string | 否 | 它在真实项目里长什么样（一句话） |

`definition` 的可验证性是整张图谱的质量命门。**写不出可验证定义的能力，不是一个原子能力，只是一个话题**，应该拆得更细或直接删掉。

### 2.4 依赖关系的三种类型

| 类型 | 语义 | 图上表现 | 用途 |
|---|---|---|---|
| `requires` | 硬前置，不满足则高难度证据打折 | 实线箭头 | 门禁、推荐排序 |
| `contains` | 组合，A 包含 B | 虚线（嵌套） | 防止粒度过粗 |
| `relates` | 软关联 | 不绘制 | 拓宽推荐 |

**DAG 约束**：
1. `requires` 不得成环（建图时校验）。
2. 跨区 `requires` 允许，且是价值所在（`perf.code-splitting requires eng.bundler`）。
3. 单个节点 `prerequisites` 不超过 3 个。超过 3 个说明它其实是 Topic，不是 Node。
4. `requires` 指向的节点必须同区或上游区，禁止"界面 requires 性能"这种倒挂（会让整张图无法线性推进）。

### 2.6 节点的生命周期

- **新增**：只加不删。旧用户的掌握度不受影响。
- **废弃**：`status = deprecated`，保留 90 天只读，之后从推荐池移除，但历史分不重算（重算会让历史记录凭空变化，用户会不信这个数字）。
- **拆分**：一个节点如果 `self_checks` 里出现明显不同能力维度，说明该拆。拆分时把原节点的证据按比例继承到子节点。
- **版本标记**：`eol_events` 记录"某版本发布后此节点的部分证据失效"，触发一次性的掌握度折损（见 3.5）。

## 3. 掌握度模型（核心）

### 3.1 分层覆盖公式

对节点 n：

```
M(n) = 100 × Σ_d ( w_d × cov_d ) / Σ_d w_d        d ∈ {D1, D2, D3, D4}

cov_d = min(1, S_d / T_d)
  S_d = 该难度层所有有效证据强度之和（同一天同层只取最大值，见 4.5）
  T_d = 该难度层的满分阈值
  w_d = 该难度层权重
```

| 层 | 含义 | `T_d` | `w_d` |
|---|---|---|---|
| D1 | 概念记忆、能复述 | 1.0 | 1 |
| D2 | 能脱离文档手写最小实现 | 1.5 | 2 |
| D3 | 能在真实代码里排错、能说清边界 | 2.0 | 3 |
| D4 | 能做架构取舍、能给别人定方案 | 2.5 | 4 |

`Σw_d = 10`。

**这个设计的效果**：只刷 D1（`cov₁ = 1`，其余 0）→ `M = 10`。哪怕你把 D1 的所有题刷十遍也还是 10 分，因为 `cov` 封顶在 1。要往上走，只能去拿更高难度的证据。

### 3.2 证据类型与基准强度

| 证据类型 | 典型行为 | 基准强度 | 可计入的最高层 |
|---|---|---|---|
| `read` | 读文档/看视频 + 记笔记 | 0.2 | D1 |
| `quiz` | 自测题全对（一组 3 题） | 0.4 | D2 |
| `explain` | 讲给 AI，通过三层追问 | 0.6 | D4 |
| `demo` | 写一个最小可运行示例 | 0.6 | D2 |
| `fix` | 在真实代码里用它修 bug | 0.8 | D3 |
| `design` | 在项目里承担该能力的决策并被评审 | 1.0 | D4 |
| `review` | 评审别人的代码，指出该能力相关问题 | 0.8 | D3 |

注意 `explain` 的"最高层"是 D4 但基准强度只有 0.6 —— 讲解是**通行证**，不是**满分卡**。要拿 D4 的 `cov`，通常需要 2–3 次高质量的讲解或一次真实决策。

### 3.3 前置门禁

```
若存在 p ∈ prerequisites(n) 且 M_eff(p) < 60：
    D3、D4 层的证据强度 × 0.5 计入
    并且不给惩罚分，只是少加分
```

**为什么打折而不是拒绝**：拒绝会让人放弃（"我明明会为什么不给分"）；打折则在保留动力的同时，让"跳级背答案"无法拿到高分。折扣力度 0.5 是经验值：一次真实 D3 证据仍能带来 0.4 的 `cov` 增量，不至于白干。

### 3.4 置信度

```
C(n) = 1 - exp( -Σ(所有层证据强度) / 2 )
```

| Σ强度 | C | 界面表现 |
|---|---|---|
| 0.6 | 0.26 | 灰色环 + "未验证" |
| 2.6 | 0.73 | 正常色环 |
| 5.0 | 0.92 | 实心环 + "已巩固" |

规则：`C < 0.4` 时**不显示掌握度数字**，只显示"未验证"。这条规则专门用来防止新用户第一眼看到一片 0 分就关掉 App。

### 3.5 衰减（双参数）

```
M_eff(t) = M(n) × 0.5 ^ ( Δt / h_n ) × Π(0.7 ^ 已触发的 eol_event 数)
```

- `h_n` = `memory_half_life`，**记忆衰减**：纯粹因为久未复现。
- `eol_events` = **技术过时**：事件驱动，不随时间。某框架大版本发布后，命中节点的 M 一次性 ×0.7，需要重新验证才恢复。

半衰期取值（v0.1 的 0.92/7天 太粗，这里分领域）：

| 类别 | `h` (天) | 依据 |
|---|---|---|
| 语言基础（作用域、闭包、原型） | 365 | 十年不变，忘得慢 |
| 浏览器原理（渲染、事件） | 540 | 稳定，但概念抽象，易模糊 |
| CSS 布局 | 730 | 最稳定 |
| TypeScript 类型系统 | 270 | 稳定但用得少时会钝 |
| 框架 API（组件、hooks、路由） | 180 | 版本节奏快 |
| 工程化工具链（构建、包管理） | 120 | 两年换一代 |
| 性能优化手段 | 240 | 指标稳定，手段随浏览器演进 |
| 可访问性 | 365 | 标准稳定 |

`0.5^(Δt/h)` 的含义：一个半衰期不复现，掌握度掉一半。这比 v0.1 的"每 7 天 ×0.92"更符合真实遗忘曲线（初期掉得快——刚学的本就脆弱，但半衰期模型对初期偏乐观，所以叠加一条：**24 小时内不复现的新节点，第二天先 ×0.9 再进入长周期**）。

### 3.6 数值示例

节点 `js.event-loop`，`job_weight = 4`，`h = 540`，前置 `js.microtask-order` 的 `M_eff = 72`（≥60，门禁不触发）。

今日证据：

| 证据 | 层 | 强度 | 累计 S_d |
|---|---|---|---|
| 读 MDN + 笔记 | D1 | 0.2 | |
| 3 道自测全对 | D1 | 0.4 | S₁ = 0.6 |
| 写最小示例并解释输出顺序 | D2 | 0.6 | S₂ = 0.6 |
| 修了一个 setTimeout 顺序 bug | D3 | 0.8 | S₃ = 0.8 |

```
cov₁ = min(1, 0.6/1.0) = 0.6
cov₂ = min(1, 0.6/1.5) = 0.4
cov₃ = min(1, 0.8/2.0) = 0.4
cov₄ = 0

Σ(w·cov) = 1×0.6 + 2×0.4 + 3×0.4 + 4×0 = 0.6 + 0.8 + 1.2 = 2.6
M = 100 × 2.6 / 10 = 26
C = 1 - e^(-2.6/2) = 0.73
```

一个相当扎实的学习日，这个节点的掌握度是 **26 / 100**。这个数字刻意偏低 —— 它传达的信息是"你入门了，但离能承担这个能力还有距离"，而不是"你完成了 100%"。

## 4. 每日评分

### 4.1 三项构成

```
日分 = 60 × I(增量) + 25 × R(巩固) + 15 × S(结构) - P(惩罚)

I = min(1, Σ_n( ΔM_eff(n) × job_weight(n) ) / 120)
R = min(1, Σ( 复现强度 × k_due ) / 2.0)
S = min(1, 今日新点亮节点数 / 2)          新点亮 = M_eff 从 0 变 ≥ 10
P = 见 4.5（默认 0，只在特定情况触发）
```

- **60% 增量**：今天真的推进了什么。基准 120 = "一个 w=3 的节点涨 40 分掌握度"。
- **25% 巩固**：把快要忘的拉回来。`k_due = 1 + log2(1 + 逾期天数) × 0.3`，逾期越久，还上越值分。
- **15% 结构**：拓宽，而不是死磕一个节点。两个新节点就满分。
- **惩罚 P**：默认 0。只在"证据被判定为伪造/复制粘贴"时触发，扣当日 30 分。日常不惩罚任何行为 —— 见 4.5。

### 4.2 完整计算（接 3.6 的例子）

同一天还做了两件事：复现了一个 21 天没碰的 `css.grid`（强度 0.7，逾期 3 天 → `k=1.52`），复现了一个按时到期的 `web.storage`（强度 1.0，`k=1.0`）。

```
I = min(1, 26 × 4 / 120) = min(1, 0.867) = 0.867
R = min(1, (0.7×1.52 + 1.0×1.0) / 2.0) = min(1, 2.064/2) = 1.0
S = min(1, 1/2) = 0.5

日分 = 60×0.867 + 25×1.0 + 15×0.5 = 52.0 + 25.0 + 7.5 = 84.5 → 84
```

### 4.3 分档语义

| 区间 | 语义 | 界面文案 |
|---|---|---|
| 0–29 | 只在消费内容，无证据 | "今天读了不少，但还没变成能力" |
| 30–49 | 弱推进 | "动了，但都是 D1 层的记忆" |
| 50–69 | 有效推进 | "有实打实的进展" |
| 70–84 | 强证据日 | "今天拿到了 D3 以上的证据" |
| 85–100 | 结构级进展 | "跨节点连接或架构级决策" |

拿到 90+ 的典型路径：做一次 D4 证据（`design`，强度 1.0 一次就占 `cov₄ = 0.4`，直接贡献 1.6 分掌握度），或者同时点亮 2 个新节点。**这保证了高分本身是有难度的，也就有信息量。**

### 4.4 边界情况

- **纯复习日**（没有新节点）：`I=0`，上限 `25+15=40`。这会让"认真复习"看起来很低分 —— 是刻意的吗？**不是，这是个 bug。** 修正：纯复习日给 `I` 一个补偿项 `0.15 × min(1, 复现节点数/4)`，让认真复习的日子落在 45–55，不至于被误读成摆烂。
- **学习时间极短但有硬证据**（20 分钟修了个线上 bug）：`I` 可能就 0.3，日分 45 左右。这个数字对他不公平，但**保护了分数的可信度**。取舍：分数不奖励"时长"，只奖励"进展"。这条如果用户不接受，说明他不是这个产品的目标用户。
- **休息日**：显式标记 `rest`，不产生日分，不计入周均分分母。

### 4.5 防刷与防通胀

| 手段 | 规则 |
|---|---|
| 同日同层去重 | 同一节点、同一天、同一难度层的多条证据，只取**最大值**，不累加 |
| 同层上限 | 任何一天对同一节点，`ΔM_eff` 不超过 15 |
| 证据必须可指认 | `demo`/`fix`/`design` 类证据必须附链接（commit / 仓库 / 截图），否则强度降级为 0.3 |
| 随机抽查 | 提交 D3 以上证据时，有 30% 概率弹一道该节点的 `misconceptions` 辨析题，答错则该证据强度 ×0.5 |
| 分数天花板锁死 | 日分硬上限 100，周报用**周均分**（按有分的天数算），避免单日刷分拉高周报 |
| 不做连续罚款 | 断签不扣分、不清零。休息日标 `rest` 即可 |

## 5. 推荐引擎（今日三件事）

### 5.1 三个槽位（固定三个，不多给）

| 槽 | 名称 | 候选池 | 目的 |
|---|---|---|---|
| 1 | 还债 | `M_eff > 0` 且距上次复现 > `0.4 × h` | 抵抗遗忘，最优先 |
| 2 | 补缺口 | 所有 `prerequisites` 的 `M_eff ≥ 60`，且自身 `M_eff` 最低 | 推进主干 |
| 3 | 拓宽 | 与最近 3 天点亮节点有 `related` 关系，或当前最弱 domain 中 `job_weight` 最高 | 防止视野收窄 |

**为什么固定三个**：选择过载是学习类产品的隐形杀手。三个是"看起来有得选、实际上不用想"的甜点。

### 5.2 排序公式

```
score(n) = 0.45 × urgency(n) + 0.35 × value(n) + 0.20 × proximity(n)

urgency   = min(1, 逾期天数 / (0.5 × h_n))          还债槽独占，其他槽为 0
value     = job_weight / 5
proximity = 1 - min(1, 图距离 / 4)                   图距离 = 与最近活跃节点的最短路
```

同分时按 `prerequisites` 满足度高者优先（更容易一次做透）。

### 5.3 每个动作必须显示"预期贡献"

界面上一张卡片长这样：

```
┌─────────────────────────────────────────┐
│ 还债 · 事件循环与任务队列                 │
│ 21 天未复现，掌握度已从 68 掉到 41        │
│ 预计 +6 ~ +9 分 ｜ 约 12 分钟             │
│ [开始]                                   │
└─────────────────────────────────────────┘
```

「预计分数区间」的估算：按该槽位典型证据强度 × 当前 `cov` 余量算出 `ΔM_eff`，再代入 4.1 的 `I` 或 `R`。区间宽度取 ±30%，**不要给精确值** —— 精确值会让用户为了那 0.5 分反复试。

## 6. 证据采集（低摩擦是生死线）

### 6.1 五类证据的采集成本

| 证据 | 采集方式 | 耗时 | 摩擦 |
|---|---|---|---|
| `read` | 一键勾选"我读完了"，可选附笔记链接 | 5s | 极低 |
| `quiz` | 3 题，机器判卷 | 90s | 低 |
| `explain` | 语音/文字讲给 AI，三层追问 | 3min | 中 |
| `demo` | 粘贴代码或贴仓库路径，自动跑 | 5min | 中高 |
| `fix` / `design` | 贴 commit / PR 链接 + 一句话说明 | 30s | 低（但要先有真实工作） |

设计原则：**每一个证据入口都必须能在一句话内完成**。任何"填写表单超过 3 个字段"的证据录入，实际使用率会掉到 5% 以下。

### 6.2 自测题设计规范

这是内容里最容易被做烂的部分，所以给硬规范：

- **一组 3 题，2 分钟内做完**，超时自动提交（防走神）。
- **题型只用三种**：给定代码说输出（对应 D1）、补全/改错（D2）、"什么情况下这个方案会失效"（D3）。
- **不要选择题占比超过 1/3**。选择题适合 D1（识别），对 D2/D3 基本无效。
- **每题必须有一个干扰项来自该节点的 `misconceptions`** —— 让"常见误区"变成"可检测的错误"。
- **同一组题不得在 30 天内重复出现**。
- 判卷：客观题机器判，`改错题` 用"是否命中关键差异点"的关键词+语义判定，允许用户申诉（申诉成功则该证据恢复满分并记录，用于改进判卷）。

### 6.3 讲解判定 rubric（`explain` 证据）

| 维度 | 权重 | 判定标准 |
|---|---|---|
| 准确性 | 25 | 有无事实错误、有无混淆相邻概念 |
| 边界感 | 25 | 是否说出"什么时候不适用" |
| 类比质量 | 25 | 类比是否让对方能懂，且不越界 |
| 抗追问 | 25 | 三层追问后是否自洽、能否承认不确定 |

低于 60 分不计证据；60–79 计 0.4；80+ 计 0.6 并可按 3.2 计入 D4。**AI 必须引用用户原话作为扣分依据**，否则不可信。

## 7. 数据模型

```sql
-- 图谱本体
create table node (
  id            text primary key,           -- 'js.event-loop'
  domain        text not null,
  topic         text not null,
  name          text not null,
  definition    text not null,              -- 必须是可验证的一句话
  why           text not null,
  job_weight    int  not null check (job_weight between 1 and 5),
  memory_half_life int not null,            -- days
  status        text not null default 'active',  -- active | deprecated
  evidence_ladder jsonb not null,           -- 各难度层可接受的证据类型
  self_checks   jsonb not null,
  misconceptions jsonb not null
);

create table node_edge (
  from_id text references node(id),
  to_id   text references node(id),
  type    text not null,                    -- requires | contains | relates
  primary key (from_id, to_id, type)
);

-- 证据与掌握度
create table evidence (
  id         bigserial primary key,
  user_id    uuid not null,
  node_id    text references node(id),
  type       text not null,                 -- read|quiz|explain|demo|fix|design|review
  difficulty int  not null check (difficulty between 1 and 4),
  strength   numeric(3,2) not null,         -- 实际计入强度（可被折扣）
  base_strength numeric(3,2) not null,      -- 原始强度，便于审计
  artifact_url text,                        -- 链接，缺省时强度降级
  gated      boolean default false,         -- 是否被前置门禁打折
  created_at timestamptz not null default now()
);
create index on evidence (user_id, node_id, created_at desc);

create table mastery (
  user_id    uuid not null,
  node_id    text references node(id),
  m          numeric(5,2) not null,         -- 未衰减掌握度
  confidence numeric(3,2) not null,
  last_verified_at timestamptz,
  updated_at timestamptz not null default now(),
  primary key (user_id, node_id)
);

-- 每日
create table daily_score (
  user_id  uuid not null,
  date     date not null,
  i_part   numeric(5,2),
  r_part   numeric(5,2),
  s_part   numeric(5,2),
  penalty  numeric(5,2) default 0,
  score    int,
  kind     text default 'study',            -- study | rest
  primary key (user_id, date)
);

create table daily_action (
  user_id uuid, date date, slot int,        -- 1..3
  node_id text, reason text, est_low int, est_high int,
  done boolean default false
);
```

`mastery.m` 存未衰减值，`M_eff` 查询时惰性计算（`0.5^(Δt/h)` 在 SQL 里一行就能算），**不做定时任务全表刷新** —— 180 节点 × 用户数的定时扫描会随规模线性增长，惰性计算是常数成本。

### 8.2 地图形态的取舍

**不用六边形雷达图。** 理由：
1. 雷达图面积随维度数量变化而失真，六区和八区的图不可比；
2. 雷达图表达不了"节点级"信息，而用户真正想知道的是"我要不要学合成层"；
3. 雷达图的六个点之间没有语义，用户看完只有"形状挺好看"。

**用"分区亮度条 + 树"**：一线一个区，条的长度是区内加权平均掌握度，展开是 Topic → Node。移动端天然友好，且能一路下钻到可执行的动作。

### 8.3 节点详情

```

│ 事件循环与任务队列        weight 4/5  │
│ 掌握度 26 / 100   置信度 0.73         │
│ ○ 概念记忆   ██████░░░  60            │
│ ○ 手写实现   ████░░░░░  40            │
│ ○ 排错应用   ████░░░░░  40            │
│ ○ 架构决策   ░░░░░░░░░   0            │
├──────────────────────────────────────┤
│ 你什么时候会用到                       │
│ 动画掉帧、setTimeout 顺序不对、        │
│ 接口回来得比预期晚……                   │
├──────────────────────────────────────┤
```

分层显示的四条进度条是整个界面的核心：它把"掌握度 26"这个抽象数字，拆成了"我卡在哪一层"。这是能力图谱相对其他学习产品最实际的价值 —— **它不只告诉你分数低，还告诉你低在哪个维度。**

## 9. 冷启动：40 个节点怎么造出来

### 9.1 流程与工时

| 步骤 | 做法 | 工时 |
|---|---|---|
| 1. 语料 | 抓 200 份前端 JD，按技能词频聚类，得出 `job_weight` 分布 | 3h |
| 2. 骨架 | 用 MDN 目录 + 官方文档目录映射出 Topic 结构，人工合并同义项 | 4h |
| 3. 拆节点 | 每个 Topic 拆到"可验证"粒度，写 `definition` 和 `why`（AI 起草 + 人工过） | 8h |
| 4. 建边 | 标 `requires`，跑环检测，检查是否有 >3 前置（有则拆成 Topic） | 3h |
| 5. 出题 | 每节点每层 2 题，共 40×4×2 = 320 题 | 12h |
| 6. 误区 | 每节点 2 条，从真实 bug 报告和面试反馈里捞 | 4h |
| **合计** | | **34h ≈ 4 个工作日** |

AI 起草能压到 12–15h，但第 3 步和第 5 步**必须人工过一遍** —— 这是内容质量的唯一保障，也是最不该省的地方。

### 9.2 只做 40 个的理由

180 个节点的图谱，如果有一半内容质量不过关，用户第一次点开发现定义含糊、题目离谱，就会永久流失。40 个高质量节点只覆盖两个区，看起来单薄，但每个节点都经得起点开 —— 这在早期比"看起来很全"重要得多。

补区的节奏：每 2 周补一个区，用真实用户行为（哪些节点被点开最多、哪些证据提交最多）来决定下一批做哪些节点。

## 10. MVP 裁剪

| 版本 | 做什么 | 不做什么 | 验收 |
|---|---|---|---|
| v0.1 | 40 节点、D1/D2 证据（read+quiz+demo）、分层掌握度、日分（三项）、地图列表视图、今日三件事 | D3/D4 证据、AI 讲解、语音、跨职业、社交 | 自己连用 14 天，日分波动符合直觉 |
| v0.2 | D3 证据（fix）、前置门禁、衰减双参数、置信度 | 同上 | 两周后老节点的掌握度自然下滑，且下滑幅度可解释 |
| v0.3 | `explain` 证据（AI 追问 + rubric）、D4 证据（design） | 语音、团队 | 同一个节点用"讲"拿到 D4，分数与"做题"路径一致 |
| v0.4 | 第二个职业的图谱（30 节点试水） | — | 引擎零改动，仅换数据 |

v0.1 砍掉 D3/D4 的代价：分数上限受限（`cov₃₊₄ = 0` 时最高 M = 60），但 v0.1 阶段用户自己也拿不到高难度证据，所以不影响体感。

## 11. 已知弱点（不打算在这一版解决的）

1. **D4 证据无法自动验证。** `design` 类证据（"我负责了这个架构决策"）几乎只能靠自述 + 评审人背书。目前只能靠"随机抽查辨析"降低造假收益，不能根治。
2. **图谱粒度是主观的。** "闭包"算一个节点还是拆成"闭包捕获"和"闭包在循环里的经典坑"？没有客观答案。判断标准只能是"拆开后能否各自出可验证的题"。
3. **跨职业复用时，`evidence_ladder` 需要重新设计。** 前端有 Lighthouse、有 commit、有可运行产物；法学、医学没有。第 3.2 节那张表是前端特有的，换领域要重做，这比换图谱本身更费事 —— 这是"引擎 100% 复用"这句话里唯一的水分。
4. **低分对坚持的伤害。** 一个诚实的能力图谱，会让用户在很长一段时间里看到满屏 20–30 分。产品层面必须用"置信度""分层进度""距离下一个节点的距离"来缓冲，而不是用虚高的分数安慰他。这条是这类产品的根本矛盾，无法彻底解决，只能管理。
