# 前端学习 + 每日评分 App：五版设计

> 版本：v0.1 ｜ 日期：2026-11-15 ｜ 定位：产品方向探索，不含实现代码

---

## 0. 先说清楚要解决什么

### 0.1 三个真实痛点

1. **学的碎片化**：今天看事件循环，明天读一篇 CSS 容器查询，后天跟着教程撸个 hooks demo。三个月后能说出很多名词，但"我会不会写"这个问题答不上来。
2. **进步不可见**：每天都在学，却没有任何东西能告诉你"这周比上周强在哪"。学习是长期低反馈的事，而人脑对延迟反馈极不敏感 —— 这是绝大多数人放弃的真正原因，不是懒。
3. **自我评估失真**：看完教程时的"我懂了"和真正能写出来之间，差着一条河（Dunning-Kruger 效应在编程学习里尤其明显，因为"读代码"和"写代码"调用的是不同能力）。

### 0.2 所以"每日评分"到底在评什么

这是整份文档最关键的判断：**评分的本质，是用可验证的证据替换主观感受。**

如果分数只来自"我今天学了 2 小时"，那它测的是勤奋，不是能力，而且第一个月就会通胀成没意义的数字（人人都 90 分）。**分数必须有"挣不来"的上限**，也就是必须存在能让你今天拿低分的机制。

下面五版设计，差异不在界面，而在**"分从哪来"**这件事上。这是五条不同的评分哲学。

### 0.3 五版一览

| | 名称 | 分数来自 | 一句话 |
|---|---|---|---|
| A | 能力图谱 | 证据累积 + 遗忘衰减 | 学习是点亮一张地图，分数是地图的亮度 |
| B | 每日评分卡 | 有效投入 × 质量系数 | 像记手账一样记学习，分数是今天的自我交代 |
| C | 造物式学习 | 可运行的交付物 | 每周造一个东西，分数由东西的质量决定 |
| D | 费曼对练 | 解释的质量 | 每天教 AI，AI 装傻追问，分数是它懂没懂 |
| E | 知识债 | 债务偿还率 | 学过的都会忘，分数是今天还了多少债 |

五版不是互斥的菜单，最后一节会给出我认为对的组合方式。

## 1. 方案 A：能力图谱（Capability Graph）

### 一句话定位
一张前端能力地图，学习就是点亮节点，每日评分是"地图今天变亮了多少"。

### 反对什么
反对"课程列表式"学习。课程告诉你"接下来学什么"，但没人告诉你"你已经会什么、还差什么才能胜任工作"。

### 核心机制
1. **能力图谱**：把前端拆成约 120–200 个原子能力节点（例：`闭包`、`this 绑定`、`事件循环`、`Flex vs Grid 选择`、`HTTP 缓存策略`、`打包体积拆分`、`无障碍语义化`）。
2. **节点间有前置依赖**：学了 `Promise` 才能学 `async/await`，学了 `事件循环` 才能理解 `微任务时序`。图谱是一张 DAG。
3. **每个节点有掌握度 0–100**，只能通过"证据"提升，且会随时间衰减。
4. **每日评分** = 今日所有证据带来的"地图亮度增量"，再折算成 0–100。

### 每日评分模型

```
证据强度 E ∈ [0, 1]，按证据类型给基准值：
  看懂了 / 记了笔记            0.2   （弱证据）
  做对了 3 道自测题            0.4
  手写实现了一个最小示例        0.6
  在真实代码里用它修了个 bug    0.8
  给别人讲清楚 / 通过追问      0.9
  在项目里承担了该能力的决策    1.0   （强证据）

难度权重 D：
  D1 概念记忆 1.0 ｜ D2 手写实现 1.5 ｜ D3 调试排错 2.0 ｜ D4 架构决策 3.0

节点掌握度 = clamp( Σ(E × D) × 100 , 0, 100 )
遗忘衰减：每 7 天未复现，掌握度 × 0.92（框架类 × 0.85，更快）

每日分 = A(今日新增掌握度总量) × 40 + B(今日复现/巩固节点占比) × 40
        + C(今日新点亮节点数 / 3) × 20
```

分数语义：<40 只是消费内容 ｜ 40–69 在推进 ｜ 70–85 有硬证据 ｜ >85 触及 D3/D4 级别

### 用户每天看到的
- **主页**：一张缩略的能力地图（按"语言基础 / 浏览器与网络 / 框架 / 工程化 / 性能与可观测 / 无障碍与设计还原"六大区着色），暗的 = 没碰过，亮的 = 掌握。
- **今日卡片**：系统推荐的 3 个动作（"补一个前置缺口""复现一个 14 天没碰的节点""推进一个相邻新节点"），每个动作标好它能带来多少分数 —— 这一点很重要：**让分数可预期，但不可伪造**。
- **节点详情**：这个能力的证据清单、常见误区、可验证的自测题、真实项目里的出现位置。

### 前端领域如何落地内容
- 图谱初版手工整理 120 节点即可（参考 MDN 目录、State of JS 调查、主流岗位 JD 的交叉高频项）。
- 每个节点配 1 个最小可验证任务（"用 20 行内实现 debounce 并说出它和 throttle 的取舍"），这是内容成本的大头，但一次投入长期复用。

### 扩展到其他职业
极其自然：**换图谱就是换职业**。后端换一张（数据库、并发、分布式、消息、缓存），产品经理换一张（需求洞察、优先级、数据分析、干系人），设计换一张。引擎完全不动 —— 这是五版里扩展性最好的。

### 技术要点
- 表：`skill_node(id, domain, parent_ids[], weight)`、`evidence(id, user, node, type, D, created_at)`、`mastery(user, node, score, last_verified_at)`
- 衰减用定时任务或查询时惰性计算（惰性更省，推荐）
- 关键难点在**内容**不在代码：图谱的粒度和依赖关系画错，整个产品就变成花架子。

### 风险
- 图谱是"别人告诉你的能力定义"，容易变成另一种课程大纲的变体。缓解：允许用户自建节点、允许"我在公司里用到了 X"作为证据。
- 冷启动重：第一版要有 120 节点才能看，做不完就上不了线。

### 什么信号说明该选它
你能接受前期 2–3 周纯内容投入，且相信"结构感"是这类用户的核心诉求（前端学习者普遍有强烈的"我是不是漏了什么"焦虑）。

## 2. 方案 B：每日评分卡（Daily Scorecard）

### 一句话定位
把"每天给自己打个分"做成一个 60 秒的仪式，分数是习惯的复利曲线。

### 反对什么
反对"学习 App 都在做内容"。内容你永远做不过 B 站、官方文档和 YouTube；但**没有人替你做"今天到底算不算有效学习"的裁决**。

### 核心机制
1. 每天结束时（或第二天早上），用 60 秒填一张卡：今天学了什么、以什么方式、产出是什么、自评。
2. 系统把自评和客观数据（如果有）合成一个 0–100 的日分。
3. 日分 → 周线 → 月趋势，形成"学习心电图"。
4. 每周日自动生成复盘：本周高分日有什么共性、低分日发生了什么。

### 每日评分模型

```
基础分 = min(有效时长 / 90min, 1) × 55
  有效时长只计"番茄内且非被动消费"的时间：看视频 ×0.5，读文档 ×0.8，
  写代码 ×1.0，调试 ×1.2，输出（写笔记/做 demo/讲给别人）×1.3

质量系数 Q ∈ [0.6, 1.4]
  + 有可指认的产出（代码/笔记/一个能跑的东西）  +0.3
  + 完成了昨日定的今日目标                      +0.2
  + 触达了 D3/D4 难度（排错、设计取舍）          +0.2
  - 全程被动观看、无任何输出                     -0.3
  - 反复在舒适区（重看已会内容）                 -0.2

连续性 M = 1 + min(streak, 10) × 0.015    （上限 1.15，且只在 Q≥1.0 时生效）

日分 = clamp(基础分 × Q × M, 0, 100)
无效日：休息日标记为 "N/A"（不计 0 分、不破 streak），主动选择的休息是合法的
```

### 用户每天看到的
- **填卡界面**：3 个必答 + 1 个可选的语音/文字补充。必答就是"学了什么/怎么学的/产出了什么"。
- **今天的分**：一个大数字 + 一句系统评语（"今天 78 分：有效时长 70 分钟，有一份可运行产出，但没碰排错类任务"）。
- **趋势页**：热力日历（类似 GitHub 贡献图，但深浅是分数不是次数）+ 30 日折线。

### 为什么这版可能赢
它**不解决学什么，只解决"今天算不算"**。这个切口极窄，因此极易做出 MVP（一周能上线），而且它和任何内容源都不冲突 —— 你看 B 站也好、看书也好，都能记在这张卡上。这是五版里**冷启动最轻**的一个。

### 扩展到其他职业
天然通用：卡片模板按领域换字段（设计师填"出了几版稿/做了什么探索"，销售填"触达数/有效对话"）。引擎 100% 复用。

### 技术要点
- 表：`daily_card(user, date, learned, method, output, duration, self_rating, score)`、`goal(user, date, text, done)`
- 无可避免的软肋：**主观输入**。缓解手段是"产出可链接"（附上 commit / 笔记链接 / 截图），有链接的卡片 Q 加成，纯口述的不给满 Q。

### 风险
- 打分疲劳：任何"每天要填"的东西，第 3 周开始衰减。缓解：允许"一键补卡"（昨天的分今天补）、允许一句话极简模式、绝不做连续打卡强迫（用 N/A 而非 0）。
- 分数通胀：用户会学会给自己打 90 分的填法。缓解：Q 的减分项要显性化，直白告诉用户"这样填拿不到高分"。

### 什么信号说明该选它
你想最快验证"用户是否愿意每天为学习打一次分"这个核心假设。这条假设是整类产品的地基，比任何花哨功能都值得先测。

## 3. 方案 C：造物式学习（Build-to-Learn）

### 一句话定位
不以"知识点"为单位，以"能跑起来的东西"为单位；分数由产物质量自动判定。

### 反对什么
反对"学完再做"。真实的能力增长发生在"做"里，而且前端有一个别的领域没有的礼物：**产物质量可以被机器客观测量**。

### 核心机制
1. 每 1–2 周一个 Build 任务（例：48 小时内做一个带骨架屏的无限滚动列表；一周内做一个响应式商品详情页，Lighthouse 性能 ≥ 90、对比度全部合规）。
2. 用户交付一个仓库地址或部署链接。
3. **系统自动跑一组客观检查**，生成质量分：能构建、能跑、有测试、体积在阈值内、Lighthouse 分数、无障碍违规数、响应式断点截图对比。
4. 每日评分 = 当日推进入度 × 当前产物质量系数。

### 每日评分模型

```
每日推进分 P = 当日 commit 数（去重去噪）× 8 + 当日解决的 issue 数 × 10
              （上限 60，避免刷 commit）

产物质量系数 Qp（自动测量，0–1.2）：
  构建通过                        必备 0（不过直接 0）
  测试存在且通过                  +0.3
  Lighthouse Performance ≥ 90      +0.25（60–89 +0.1）
  Lighthouse A11y ≥ 95             +0.2
  首屏 JS 体积 < 200KB             +0.15
  响应式 3 档截图无明显破损         +0.15
  有 README 说清技术取舍           +0.15

日分 = clamp(P × Qp, 0, 100)
周期结算：每 2 周一次"交付分"，只看最终产物状态（不看过程），
          交付分决定这 2 周的平均分能否封顶到 100
```

这个设计的妙处在于：**它把"感觉学得不错"彻底替换成了"CI 是绿的、分数是 92、a11y 零违规"**。这类证据用户自己是造不了假的。

### 用户每天看到的
- **当前 Build 卡片**：目标、验收标准（就是上面那些可自动测的项）、倒计时。
- **仪表盘**：质量系数各项的实时状态（绿/黄/红），像 CI 面板。
- **雷达对比**：本次产物 vs 你上次产物的六维对比（性能/无障碍/体积/测试/响应式/文档）。

### 扩展到其他职业
中等难度。前端有 Lighthouse 这种天赐的客观测量工具；换成写作、设计、运营，客观测量要重新设计（写作可以用"结构/信息密度/可读性"的 LLM 评估，但主观性强很多）。**这版的扩展性最弱，但纵深最深**。

### 技术要点
- 需要一个能跑构建的沙箱（部署到临时环境后测，或本地 CLI 上报）
- 表：`build_task(id, title, acceptance[], difficulty)`、`submission(id, task, repo_url, scores_json, measured_at)`
- 最重的部分是**验收标准的编写**和测量流水线，不是 App 本身

### 风险
- 门槛高：初学者连"怎么交一个能测的项目"都不会，会在第一步流失。缓解：给模板仓库 + 一键初始化。
- 测量即目标（Goodhart）：为了 Lighthouse 90 分而牺牲真实工程质量。缓解：加"取舍说明"这一项，鼓励写清"我为了 90 分放弃了什么"。

### 什么信号说明该选它
你的目标用户是"已经能写点东西、想突破瓶颈"的中级前端，而不是零基础。这版对进阶者吸引力远超其他四版。

## 4. 方案 D：费曼对练（Teach-the-AI）

### 一句话定位
每天 10 分钟，你把这个概念教给一个装傻的 AI；它懂没懂，就是你的分。

### 反对什么
反对"做题验证"。选择题能测记忆，测不了理解；而**能不能讲明白，是最诚实的理解检测器**。

### 核心机制
1. 系统每天派一个"今日概念"（来自你的学习记录或图谱缺口）。
2. 你用自己的话讲 —— 文字或语音，限 3 分钟 / 300 字。
3. AI 扮演一个"聪明但完全不懂的初学者"，**只做一件事：追问**。追问分三层：为什么是这样？如果不是这样会怎样？那和我已知的 X 冲突了怎么办？
4. 你答不上来的地方，就是理解缺口。系统把它记成"待补"，并给出最小补课材料。
5. 分数由 AI 按四个维度评，且必须引用你的原话作为依据。

### 每日评分模型

```
四维各 25 分：
  准确性   有没有说错、有没有把相关概念混为一谈
  边界感   有没有说清"什么时候不适用"（区分初级和中级的分水岭）
  类比质量 有没有用对方能懂的类比，且类比不越界
  抗追问   三层追问下能否自洽、能否承认"这里我不确定"

扣分：被追问后改口超过 2 次 -10（说明本来是背的）

日分 = 四维之和 - 扣分
连续 7 天有 ≥70 分 → 该概念标记为"可讲清"（这是最强的掌握证据）
```

### 用户每天看到的
- **对话式主界面**：像在教一个学生。AI 的问题会刻意"笨一点"，比如"你说闭包能保存变量，那函数返回之后变量不是应该被回收吗？"
- **今日复盘**：3 个你卡住的地方 + 每个点一句话的正确答案。
- **可讲清清单**：你已经能给外行讲明白的概念列表 —— 这份清单本身就是很好的作品集。

### 为什么这版有意思
它把"评分"和"学习"合并成同一个动作，没有额外负担：**你不是为了打分而讲，你讲的过程就是在学**。这在五版里是唯一一个"评分即学习"的设计。

它还有个隐藏价值：语音讲解天然适合通勤、走路、做家务的碎片时间，不需要坐下来。

### 扩展到其他职业
极好。任何职业的核心能力都是"能把复杂事情讲清楚"：法学的案例解释、医学的病理讲解、销售的方案陈述、管理者的目标对齐。**只换概念库，引擎不动**。

### 技术要点
- 表：`concept(id, domain, canonical_answer, misconceptions[])`、`session(id, concept, turns_json, scores_json)`、`explainable(user, concept, verified_at)`
- 内容成本：每个概念需要"标准答案 + 常见误区清单"，AI 追问才有方向（否则追问会飘）
- 评分要可解释：每条扣分必须指向用户原话的某一句

### 风险
- AI 评分不稳定：同一段解释两次打分可能差 15 分。缓解：固定 rubric + 温度调低 + 只做四维粗评（不做精细小数点分数）。
- 用户觉得"像在被考试"，压力大。缓解：AI 的姿态必须是学生不是考官，措辞上彻底避免"你答错了"，改成"这里我没听懂，能换个说法吗"。

### 什么信号说明该选它
你愿意在 AI 调用成本上花钱（每天每人 1–3 次多轮对话），并且相信"讲解"是目标用户认可的验证方式。

## 5. 方案 E：知识债（Knowledge Debt）

### 一句话定位
学过的都会忘。这个 App 把你的记忆当成一笔要还的债，每天的分就是还款率。

### 反对什么
反对"学过 = 学会"。前端知识的半衰期差异极大：CSS 盒模型十年没变，但构建工具两年换一代。**没有人替你管理这个衰减，所以你的知识在静默贬值。**

### 核心机制
1. 每学一个知识点，入队成一笔"知识资产"，附带半衰期（按领域类型设定）。
2. 系统按间隔重复（SRS）安排复现时间：1 天 / 3 天 / 7 天 / 21 天 / 60 天。
3. 到期未复现 → 变成"逾期债"，且利息随时间增长（掌握度持续衰减）。
4. 每日评分 = 今日到期债的清偿质量 + 新债控制。

### 每日评分模型

```
单笔债：
  半衰期 h：语言基础 180d ｜ 浏览器原理 240d ｜ CSS 布局 365d
            框架 API 90d ｜ 工程化工具链 45d ｜ 性能优化 120d
  逾期天数 t → 应还难度系数 k = 1 + log2(1 + t) × 0.3

清偿质量（复现时自测）：
  完全想不起          0.0（重新入队 1 天后）
  想起来但写不出      0.4（入队 3 天后）
  能写但要查文档      0.7（入队 7 天后）
  不用查就能写        1.0（间隔翻倍）

日分 = 清偿率 × 70 + (1 - 新增债务 / 5) × 30
  其中 清偿率 = Σ(清偿质量 × k) / Σ(k)
  新增债务 = 今日新学知识点数（学太多也是问题：只进不出会崩）
  逾期债超过总资产 30% → 系统进入"只还不借"模式，今天不再推荐新内容

周结算：债务健康度 = 已巩固资产 / 总资产，<60% 时给"止血周"计划
```

### 用户每天看到的
- **今日待还**：3–7 张卡片（这就是每日任务，不需要用户决定学什么）
- **债务仪表盘**：资产总量、逾期笔数、健康度、按领域的衰减热力
- **单卡**：一个问题 + 一个"我卡住了"按钮（点它不算失败，只是记录）

### 为什么这版扎实
它把"每日评分"从**激励问题**变成了**记账问题**。人不需要被激励去还债 —— 只要数字在那里，你就知道欠着。而且它对"低分日"的解释极其自然：今天没还完，所以分数低。用户不会觉得被评价，只觉得账没平。

### 扩展到其他职业
很好。任何有"知识密集 + 需要长期记忆"特征的职业都适用（考证人群是天然市场：法考、注会、医师）。半衰期表的设定是领域知识，引擎通用。

### 技术要点
- 表：`asset(user, concept, half_life, last_review, strength)`、`review_queue(user, asset, due_at)`、`debt_snapshot(user, date, ratio)`
- SRS 算法直接借鉴 FSRS / SM-2，不要自己发明
- 最难的是**概念卡的生成**：从"我今天学了 X"自动产出一张好卡（问什么、答案的粒度），这里需要 LLM 辅助

### 风险
- **复习是反人性的**：纯 SRS 产品留存普遍很差（Anki 是最好的例子 —— 极有效，极难坚持）。缓解：把卡片做成"故事/场景"而不是问答，加入 D 版的讲解模式作为复现方式（"用 3 句话讲给我听"比"默写定义"体验好一个量级）。
- 前期无感：第一周没有债可还，分数没意义。缓解：导入期允许"补录历史学习记录"生成初始债。

### 什么信号说明该选它
你相信"遗忘"才是目标用户最大的敌人（工作 1–3 年、面试前突击、知识焦虑型用户通常如此）。

## 7. 我的判断（观点，非中立罗列）

**单独做任何一版都会缺一块。** 具体说：

- 只做 B，会变成一个"自我感动的打卡 App"，分数虚，三个月后用户发现自己的分数和真实能力无关，就流失了。
- 只做 A，会变成一张好看但不动的地图，用户找不到"今天该干嘛"的具体动作。
- 只做 E，会变成 Anki，很有效，但你留不住人。
- 只做 C，会筛掉 80% 的初学者。
- 只做 D，很惊艳，但一天只有 10 分钟，撑不起"每日学习"这个更重的场景。

**推荐的骨架是 B + A + E 的三层结构，C 和 D 作为"内容形态"而不是评分主体：**

```
外层  B 每日评分卡    → 提供"每天必须有一个数字"的仪式感和情绪反馈
内核  A 证据账本      → 决定这个数字有没有资格高。分数只能靠证据挣，不能靠时长刷
底噪  E 复习引擎      → 让内核会衰减。今天不还债，明天的分自然会掉
可选内容形态：
      C 造物（每 2 周一个 Build，作为强证据来源，接进 A 的 evidence 表）
      D 讲解（作为复现方式，替代枯燥的默写，接进 E 的清偿判定）
```

这个结构的关键是：**B 负责坚持，A 负责诚实，E 负责长期。** 三个东西各自解决一个独立问题，而且都能单独砍掉 —— 如果只能先做一个，就做 B；如果只能留一个，留 A（因为它决定了产品的灵魂）。

如果要压成一句话的定位：
> **一个每天给你学习表现打分的东西。分数靠证据挣，会随时间衰减，所以你每天都能看见自己是真的在长，还是只是看起来很努力。**

### 扩展路径（前端 → 其他职业）

三层结构里，只有 A 的"内容"是领域相关的：

| 层 | 换职业要动什么 | 复用度 |
|---|---|---|
| B 评分卡 | 只换卡片字段模板 | 95% |
| A 证据账本 | 换能力图谱（120 节点）+ 证据类型定义 | 引擎 100%，内容 0% |
| E 复习引擎 | 换半衰期表 + 概念卡 | 引擎 100% |

所以**"先做前端、再扩职业"这个顺序是对的**，因为图谱是可以逐个职业增量积累的资源，做一张是一张，且每张都构成壁垒。这也是唯一一个"做得越久越难被抄"的结构。

## 8. 六周 MVP 路线（按 B+A+E 骨架）

| 周 | 做什么 | 验收标准 |
|---|---|---|
| 1 | 数据模型 + 每日卡片录入 + 分数计算（纯手动） | 自己能连续 7 天填卡，分数不出 bug |
| 2 | 趋势页（热力日历 + 30 日线）+ 周复盘生成 | 一周数据能自动出"高分日的共性" |
| 3 | 证据账本：节点 + 证据录入 + 衰减 | 手动录入 20 条证据，掌握度曲线合理 |
| 4 | 复习队列（SRS）+ 今日待还 | 到期卡片按 SRS 正常排期 |
| 5 | 前端能力图谱 60 节点（先做前端的六大区中最常用的两个区） | 用户能看到"我还差什么" |
| 6 | 复盘 + 打磨：低分日合法化、休息日 N/A、补卡 | 自己用满两周不觉得烦 |

**要盯的四个指标**（从第一天就开始记）：
1. 填卡完成率（次日回来填昨天的比例）
2. D7 / D30 留存
3. 每周"硬证据"数量（D3 以上难度）
4. 逾期债清偿率

第 1 项低于 50% 说明评分这件事本身让人厌烦，需要砍流程；第 3 项长期偏低说明分数在通胀，需要提高 A 层权重。

## 9. 五条必须守住的设计原则

1. **分数必须有上限，且必须有人拿低分。** 一个所有人都能拿 90 分的评分系统等于没有评分系统。
2. **休息是合法的。** 用 N/A 而不是 0。用罚分逼人打卡的产品，最后留住的是"为了不断 streak 而敷衍填卡"的人，这批人会污染你所有的数据。
3. **每个分数都要能解释到具体某件事。** 不给黑箱分。用户点开分数必须看到"这 12 分来自那个 bug 修复"。
4. **不做排行榜。** 至少第一年不做。学习进度和起点强相关，排行榜会把最需要鼓励的人排到最后。
5. **数据必须可导出。** 学习记录的沉没成本焦虑是这类产品最大的隐患，反过来说，承诺可导出是最强的信任信号。

## 10. 需要你拍板的三件事

1. **主用户是"零基础转行"还是"在职 1–3 年想突破"？** 这个选择直接决定 A 版图谱的粒度和 C 版是否要存在。我倾向后者 —— 他们付费意愿更强，且"我到底会不会"的焦虑更真实。
2. **形态是 Web 还是小程序/App？** 每日填卡和还债场景对"随时打开"要求高，我倾向小程序或 App 为主、Web 做重内容（图谱、复盘）。
3. **AI 用在哪些环节、预算多少？** D 版和 E 版的卡片生成都吃 token，如果要控成本，第一版可以只让 AI 做"周复盘的一句话总结"，评分全部走规则。

这三个定了，我可以把选定方向拆成可直接开工的 PRD 和数据模型。
